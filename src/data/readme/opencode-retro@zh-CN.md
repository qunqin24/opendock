# opencode-retro

[Русский](README.md) | [English](README.en.md) | **简体中文** | [Español](README.es.md) | [日本語](README.ja.md)

> [`README.en.md`](README.en.md) 的译文。英文版为正本（canonical）；若两者不一致，以英文版为准。

面向编码智能体的复盘工具。这是一个 [OpenCode](https://opencode.ai) v2 插件，它读取已结束会话的对话记录，找出能让智能体工作得更顺的地方，并把它们转化为对项目自身工作环境的改动建议，包括其技能、说明文件与工具。

智能体不会从自己的会话中学习。它在哪里受阻，唯一的记录就是日志，而日志通常没人看。本插件负责读日志，并带回建议。

> 状态：功能完整且可用，已在 OpenCode 2.0.32 上验证。npm 包名为 `opencode-retro`；`v0.1.0` 是它第一个具备功能的版本。

## 要解决的问题

同样的障碍会在一次次会话中反复出现：

- 某个技能要求运行 linter，而项目并没有 linter。智能体照做，改写四十个文件，随后察觉，又把一切回滚。
- 说明文件要求在提交前执行构建命令，而项目并未定义这样的脚本，于是每次照办这一步都会失败。
- 代码风格没有写在任何地方，于是每次会话都要先读源码把它重新推导一遍。
- 一条失败的命令被重试数次，而两次尝试之间什么都没有改变。
- 计划中的一项任务被悄悄放下，理由是“目前做不到”。
- 同一条纠正已经连续第三周由人手动给出。

这些都在日志里，却没有一条能进入下一次会话。

## 工作方式

两个有意分开的循环。前者自行运转，不占用注意力；后者按需启动，每次给出一个决定。

### 采集

每一次工具调用与每一条提示都会追加写入影子日志 `.retro/sessions/<id>.jsonl`。此过程不涉及模型，插件只负责写入。因此该日志不受上下文压缩影响：无论会话如何处理自己的历史，原始轨迹都会保留。

### 提炼

会话结束后，它的日志会被保留；默认情况下，在未被请求之前不会发生任何事。分析需要一次模型调用，而默认情况下本插件不会在未经请求的情况下花掉它。

`/retro` 就是发生分析的那一刻。一条命令会压缩已经积累的日志，把它们变成教训，然后才去寻找可供交接的内容。一条命令会分析所有等待中的日志；`options.extractLimit` 可以限制数量，剩余数量会被告知，再执行一次 `/retro` 即取下一批。一次调用读不完的长日志会分段读取，每条命令读一段，每段都从上一段停下的地方接着读；读完之前，`selfcheck.md` 会将其标为已部分读取。

每份日志都在一个专为这次调用创建、随后即被删除的会话中分析：输入是那份日志，不涉及智能体、历史与工具，输出是文本。那个干过活的智能体被刻意排除，因为它会为自己的决定辩护。

尚未结束的会话也会被读取，包括运行该命令的这一个：它们的摩擦是最新鲜的。读取并不会了结任何事。插件记得每份日志读到了哪里，会话之后写入的内容会在下一次 `/retro` 时读取，而且只读这一部分：已经变成教训的内容不会再分析一遍。会话通常不会结束，而是一直开着、随后再回来，所以若不如此，几周后的一次 `/retro` 就会把一切重读一遍，并把早已处理过的教训重新得出一次。插件不需要知道某个会话是否仍在运行：它所知道的一切都在磁盘上的 `.retro/` 里，因此重启、崩溃，或同一项目上的第二个 OpenCode，都不会改变读取的内容。

只有在一次会话不可能包含任何证据时才会跳过而不产生调用：一条指令、一个回答、什么也没做。完全没有工具调用的对话仍会被分析，因为说明文件写错正是这样显现的——一个错误的回答加上一次纠正，而什么都没有执行。

`options.asyncExtract` 会在下一次会话开始时，在后台分析已结束的会话，而不是等待 `/retro`，供希望在询问之前就准备好教训的人使用。新会话不会因此被拖慢：分析启动后会在一个独立的会话中自行进行，处于工作上下文之外，每次提示处理一份日志。

默认情况下，分析使用所记录会话所用的模型；若尚未见到，则退回到工作区的默认模型，并在该模型有无推理变体（`none`）时请求使用它。分析只是一个结构化的回答，而推理模型若任其思考，可能会把全部输出都花在推理上，最终一个回答也不返回。这在 OpenCode 的免费层模型上同样可用，因此无需任何配置。`options.model` 可以指定另一个模型，当希望分析跑在比日常工作更便宜的模型上时值得这么做；`options.model.variant` 则可指定改用的变体。

该调用收到的是会话的压缩视图：工具输出经过大幅裁剪，提示与回复各自最多完整保留几千个字符。它只回答一个问题：

> 如果这次会话重新运行一遍，项目里应当改变什么，才能让它走得更短、更直？

答案是 `.retro/lessons/` 中的一份教训清单。

一份已结束的日志只分析一次；失败的回复会在接下来的两次运行中重试，然后被搁置。默认情况下，从不运行 `/retro` 的项目根本不会被分析。

### 提炼依据什么

判断标准并未写死在插件里。它们位于 [`prompts/extract.md`](prompts/extract.md)，首次运行时作为 `.retro/prompts/extract.md` 播种到项目中，并可在那里编辑。它们描述值得寻找的形态：

- 白做的工作：同一个调用被再次发出，而两次之间没有任何文件发生变化。
- 做出又被撤销的改动，无论是被后来的编辑覆盖，还是被丢弃工作区所抹去。
- 走进死胡同的技能：该技能所规定的命令随后失败。
- 看起来不像失败的失败：非零的退出码，藏在显示为 “completed” 的状态背后。
- 被静默放弃的任务：它只体现在智能体所写的文字里。
- 用户不得不给出一次以上的纠正。

该文件中明确写着：这是一个起点，而不是检查清单。

### 提议

插件读日志，人读建议。插件到建议为止，不会改动项目文件。

| 命令 | 作用 |
|---|---|
| `/retro` | 先分析已积累的内容，然后交付一条教训：尚未裁决者中得分最高的那条。 |
| `/retro all`（或 `/retro-all`） | 同样的分析，然后把待处理的教训作为一份计划交付，最多 `proposeLimit` 条（默认十），一次性批准。 |

没有第三条命令。插件是否在工作，写在 `.retro/selfcheck.md` 里，从每个会话的第一个提示起就会重写，会话结束时再写一次。

教训会被送进执行该命令的那次会话，并写给已经在场的智能体。首先请它判断这条教训是否仍然成立，然后转述，并且在作出决定之前不做任何改动。

```
# retro — lint-skill-no-config

lint 技能规定运行 `npx eslint . --fix`，而本项目无法执行该命令。

出现于 2 次会话，为此花费 9 步，置信度 0.9，得分 16.2。
上次出现在 3 个会话之前。

建议的改动
  AGENTS.md —— 将 lint 要求改为以仓库中已提交的 ESLint 配置为前提。

需要决定
  本项目是否应当配置 ESLint，还是应当放弃这条约定？
```

决定属于该会话中的人与智能体。智能体掌握文件、历史以及项目自身的技能，因此在判断一条教训是否仍然适用这件事上，它比插件更可靠。决定作出之后，智能体通过 `retro_decide` 工具记录结果。该工具只做记账：被否决的教训会被记住，不再重复提出。

`/retro all` 是同一种交付，只是一次面对全部。待处理的教训会被排序并一起交付，最多 `proposeLimit` 条；智能体检查哪些仍然成立，把其余的汇成一份按文件分组的计划，整份计划一次批准。

### 修改应落在何处

教训记录的是问题。在何处修改，则在交接时决定：由智能体与人一起，先看清这个工作区实际拥有什么——此处工作环境会读取哪些说明文件、项目级或全局是否存在技能、是否已有更具体的东西覆盖了这项任务。

可选的做法：

- 修改说明文件，适用于广泛生效的事实或约束。
- 修改技能，当某个技能给出了错误的步骤，或在不该触发时触发。
- 新建技能，或新建一个限定于规则实际生效目录的说明文件，当合适的位置尚不存在时。
- 请求一个工具，当缺的是能力而不是说明。
- 改动项目代码，当陷阱就在代码里。未经明确同意绝不应用。
- 暂不归位，当正确的归属确实不清楚时。

教训本身始终属于单一工作区。修改则不一定：如果原因在于此人在任何地方的工作方式，那么修改属于其全局工作环境，因为只在一个项目里修好会让其余项目仍然坏着。项目之外的任何内容都不会在未经询问的情况下被改动。

具体做法与这份清单位于 [`prompts/propose.md`](prompts/propose.md)，它会被播种到项目中并可在那里编辑。

## 教训

一条教训是一个带 YAML frontmatter 的 Markdown 文件。

```yaml
id: lint-skill-no-config
statement: The lint skill assumes eslint; this project has no linter.
evidence:
  - session: a81f
    steps: [41, 58]
  - session: c204
    steps: [12, 19]
cost: 34
recurrence: 3
confidence: 0.9
lastSeen: 41
recordedAt: 2026-10-19T15:16:04.134Z
proposal:
  target: .opencode/skills/lint/SKILL.md
  change: |
    Before running, check for a lint config and a lint script.
    If absent, do not run; report instead.
ask: Is the linter really unused here?
status: new
```

`cost` 是该问题消耗的步数，跨会话累加。`recurrence` 是它出现过的独立会话数。`lastSeen` 是最后一次写入该教训时该工作区的会话计数。

### 排序

得分为 `cost × recurrence × confidence × freshness`。

新鲜度每经过 `halfLife` 个该问题未再出现的会话便减半（默认十），并且按会话计数而非天数计算。若一天只有一次会话，按日历衰减会在一夜之间把一切埋没。

复发比单次昂贵的事故更有分量。在三次会话中出现过的问题，在第四次仍会出现。

### 生命周期

教训以问题为键，而不是以会话为键。第二次会话遇到同一件事时，只会补充其证据并把 `recurrence` 加一，而不是另建文件。

`lessons/` 只保存尚未裁决的问题。接受或拒绝会把文件移入 `archive/`，并且任何内容都不会被删除；标记为 `later` 则保持其未决。一个关闭后又回来的问题，是同一个问题，外加“此前的修法没有奏效”这一新情况，因此它会带着完整历史重新打开。固定上限为三十，用来保持列表简短；超出的部分同样进入归档，但标记为 `later` 的教训除外。

## 安装

OpenCode 会从 npm 获取插件；在 `opencode.json` 中写出包名即可：

```jsonc
{
  "plugins": [
    {
      "package": "opencode-retro",
      "options": {
        "model": { "providerID": "deepseek", "id": "deepseek-flash" }
      }
    }
  ]
}
```

`options.model` 为选填。不填时，插件会使用会话所用的模型；若尚未见到，则退回到工作区的默认模型。`.retro/selfcheck.md` 会报告分析是否运行过，以及失败时的原因。

**先看清 npm 上实际有什么。** 所有低于 `0.1.0` 的版本都只是占位：加载时不报错，不注册命令，不创建 `.retro/`，也不提示任何信息。也就是说，在第一个真正的发布之前照抄这段配置，只会得到一个看起来正常的会话和一个其实并不存在的插件。如果 `npm view opencode-retro version` 低于 `0.1.0`，请把 `package` 指向一份检出的绝对路径——开发插件本身时也是这样运行。相对路径会使会话启动一直挂起且不报任何错误；等到有版本可钉时，也可以钉住确切版本（`opencode-retro@0.1.0`）。

其余均为可选：

- `dir` —— 一切所在的目录，默认 `.retro`。
- `prompts` —— 提示文件目录，默认为其中的 `prompts`。
- `halfLife` —— 教训得分减半所需的「未再出现的会话数」，默认十。
- `proposeLimit` —— 单次 `/retro all` 中的教训数量，默认十。
- `extractLimit` —— 单次 `/retro` 分析的日志数量，默认不限。
- `maxOutput` —— 影子日志中每一步保留的工具输出字符数，默认 8000。
- `maxInput` —— 一次分析最多发送的字符数，默认 32000。过长的日志会被裁剪以适配：先减少工具输出，再从中间丢弃整步，每处空缺都会说明丢了多少步。这用于限制成本。空答案会以一半的大小再问一次，然后再以四分之一的大小问一次；仍然得不到答案的日志会在下一次 `/retro` 时重试，`.retro/selfcheck.md` 会把它标为失败。
- `extractTimeoutMs` —— 单次分析放弃前的等待时长，默认 90000。
- `heartbeatMs` —— 会话进行中两次自检写入之间的最短间隔，默认 60000。
- `keepSessions` —— 保留所有日志，包括无人引用的；默认关闭。
- `asyncExtract` —— 在下一次会话开始时分析，而不是等待请求；默认关闭。

### 磁盘上会出现什么

插件写入的一切都留在项目的 `.retro/` 之下，除接受建议的情形外不会写到别处。全部为纯文本。

```
.retro/
  prompts/
    extract.md       什么算作一条教训
    propose.md       一条教训如何交接，一条或全部
    updates/         更新后的默认值，未被使用
  sessions/          原始日志；在未读、被教训引用或本周内有写入时保留
  lessons/           尚未裁决的问题
  archive/           已接受、已拒绝与被挤出的教训
  selfcheck.md       插件是否在工作
  state.json
  plugin.log         钩子、命令与后台工作的错误
  .gitignore         只写入一次，此后归项目所有
```

当三件事同时成立时，日志才会被删除：它已被读到末尾，没有未裁决的教训引用它，并且七天内没有任何写入。教训的证据会指明某次会话及其中的步数区间，而在复核时，“那里到底发生了什么”这个问题必须有一个不是概述的答案，因此被引用的日志会保留。正是这七天，使得在不知道会话是否仍在运行的情况下删除也是安全的：持续写入的会话会保留自己的日志，而沉寂一周后被重新拾起的会话会开始一份新日志，并从头读取。没有人读过的日志，无论多旧都不会被删除。增长由未裁决教训的数量（该数量有上限）和一周的会话决定，而不是由项目的存续时间决定。

无需在项目的 `.gitignore` 中添加任何内容。插件在首次运行时写入 `.retro/.gitignore`，git 会将其应用于其下的一切：会话、状态、自检、插件日志、提示更新通知以及崩溃留下的未写完的 `.tmp` 文件被忽略，而 `lessons/`、`archive/` 与生效的提示文件不会。该文件只写入一次，此后即归项目所有。

这种划分是设计而非便利。教训与归档属于关于项目的知识：可读、出现在评审中、随仓库流转。提示文件是项目的配置，值得与在此工作的其他人共享。其余内容只会在 diff 中制造噪音。

### 提示文件

插件的行为由两个提示决定，两者都是项目内的文件：什么算作一条教训，以及一条教训如何交接。后者也涵盖成批的情形：`/retro all` 发送的是同一条规则，其最后一节说明当多条教训同时到来时有什么不同——一份计划、按文件归并、被放弃的逐条点名。一条规则，而不是每个命令一条，这样修改它就不会留下另一份与它不一致的副本。

每个提示在首次运行时由随包的默认值播种，之后不再被写入。解析顺序为先项目，再 `~/.config/opencode/retro/prompts/`，最后是随包默认值，因此一个提示可以为某一个项目固定、为所有项目固定，或都不固定。

当更新后的默认值发布时，它会以 `prompts/updates/<name>.vN.md` 的形式出现，文件开头注明该文件并未被使用。不会有任何内容代替用户被应用。

留在源代码中的是机械部分：解析器所要求的输出格式、教训字段的顺序，以及记录决定的指示。输出格式从不写入磁盘，因此编辑提示文件无法移除解析器所需的格式。

## 确认它在工作

钩子注册成功并不能证明任何事。以 API 中已不存在的名称注册的钩子，会注册成功，然后永远不触发。

因此 `.retro/selfcheck.md` 报告的是存活状况而非安装状况：它把事件流所见与钩子所收到的内容相互对照。该文件自带过期规则：

> 如果工作正在进行，而 `heartbeat` 已超过几分钟，则插件没有在运行。

这些检查在每次复核时运行且不产生任何花费：插件所依赖的 API 构成、当前生效的是哪一层提示，以及有什么在等待裁决；插件与 OpenCode 的版本则写在文件抬头。模型是否响应、输出格式是否仍可解析则不单独询问——每次分析都会实际检验这两件事，而无法解析的回复会用模型自己的话报告。

## 运行要求

- OpenCode v2，`@opencode/plugin` 2.0.18 或更新版本。已在 2.0.32 上验证。
- 除 OpenCode 本身之外无需其他。分析默认使用会话自身的模型；低成本模型即可。
- 无运行时依赖。
