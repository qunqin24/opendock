# opencode-retro

[Русский](README.md) | [English](README.en.md) | [简体中文](README.zh-CN.md) | [Español](README.es.md) | **日本語**

> [`README.en.md`](README.en.md) の翻訳です。英語版が正本（canonical）であり、内容が食い違う場合は英語版が優先されます。

コーディングエージェントのための振り返りツール。終了したセッションの対話を読み、エージェントの働きを改善できる点を見つけ、それをプロジェクト自身のハーネス、すなわちそのスキル、指示書、ツールへの変更案に変える [OpenCode](https://opencode.ai) v2 プラグインです。

エージェントは自分のセッションから学びません。どこでつまずいたかを示す記録はログだけであり、そのログは読まれないままになります。このプラグインがログを読み、提案を持って戻ります。

> 状態: 実装は完了して動作します。OpenCode 2.0.32 上で検証済み。npm パッケージは `opencode-retro`、`v0.1.0` が機能を備えた最初のリリースです。

## 解決したい問題

同じ障害がセッションごとに繰り返されます。

- あるスキルがリンターの実行を指示する。しかしプロジェクトにリンターはない。エージェントはそれでも実行し、四十個のファイルを書き換え、気づいて、すべてを巻き戻す。
- 指示ファイルがコミット前のビルド実行を求める。プロジェクトにそのスクリプトは定義されておらず、従うたびにこの手順は失敗する。
- コードのスタイルがどこにも書かれていないため、毎回のセッションがまずソースを読んで導き直す。
- 失敗するコマンドが数回再試行されるが、試行の間に何も変わっていない。
- 計画中のタスクが「今は不可能」として静かに取り下げられる。
- 同じ訂正が三週間続けて手作業で与えられる。

これらはすべてログの中にあります。そしてどれも次のセッションには届きません。

## 仕組み

意図的に分けられた二つのループがあります。前者は自動で進み、注意を必要としません。後者は要求に応じて動き、一度に一つの判断を生みます。

### 収集

すべてのツール呼び出しとすべてのプロンプトが、シャドーログ `.retro/sessions/<id>.jsonl` に追記されます。モデルは関与せず、プラグインは書き込むだけです。そのためこのログはコンテキストの圧縮から独立しており、セッションが自身の履歴をどう扱っても、生の軌跡は残ります。

### 抽出

セッションが終わると、そのログは保存され、求められるまで何も起こりません。分析にはモデル呼び出しが必要で、このプラグインは求められないかぎりそれを消費しません。

`/retro` がその瞬間です。溜まったログ一つずつに**作業指示書**を書きます。`.retro/work/` に置かれるファイルで、そのログを指し示し、どの部分が新しいかを述べ、判断の基準と答え方を携えています。そして、あなたがコマンドを実行したセッションのエージェントに、指示書を一つずつ別々のサブエージェントに読ませるよう頼みます。待機中のログはすべて一つのコマンドで指示書を受け取ります。`options.extractLimit` で件数を制限でき、残りは報告されるので、次の `/retro` が続きを引き受けます。

指示書はログを含みません。指し示すだけです。読むのはサブエージェントの仕事であり、どう読むか——一度に全部か、まず冒頭、それから先へ——は、プラグインが外から当てる規則よりもサブエージェントのほうがうまく決められます。一部しか読めなかったサブエージェントはそう申告し、残りは引き続き未読のままです。`selfcheck.md` はそのログを一部読了として示し、次の `/retro` が残りについて尋ねます。

各指示書は、一つのサブエージェントが自分のコンテキストで読みます。プラグインはモデルを呼ばず、選びもしません。読む作業はあなたのセッションのモデルと設定の上で、OpenCode 自身のエージェントループで進みます。分析される作業を行ったエージェントは意図的に除かれます。自分の判断を弁護してしまうからです。サブエージェントはそのセッションにいなかったので、弁護すべきものを何も持ちません。

答えは `retro_record` ツールの呼び出しで、そのスキーマが出力形式そのものです。形の崩れた答えはプラグインに届く前に OpenCode が拒み、理由がサブエージェントに伝えられるので、やり直せます。教訓が一つもない答えも立派な答えです。そのセッションは真っ直ぐ進んだということです。記録が揃うと、エージェントが `retro_propose` を呼び、それがあなたに教訓を差し出します。誰も答えなかった指示書は、ログのせいにはされません。沈黙から何かを結論づけることはしません。ここから見ると、読んで記録できなかった読み手と、そもそも始まらなかった読み手は区別できないからです。次の `/retro` が改めて求め、`selfcheck.md` が「そのログを何回尋ねて答えがなかったか」を伝えます。

まだ終わっていないセッションも読まれます。コマンドを実行したこのセッションも含みます。そこにある摩擦がいちばん新しいからです。読んだからといって何かが確定するわけではありません。プラグインは各ログをどこまで読んだかを覚えており、セッションがその後に書いたものは次の `/retro` で読まれます。読まれるのはその部分だけで、すでに教訓になった部分は二度は分析されません。セッションは終わらせずに開いたままにして後で戻る、というのが普通の使い方ですから、そうしなければ数週間後の `/retro` が全部を読み直し、すでに対応した教訓をもう一度導き出すことになります。プラグインは、セッションがまだ動いているかどうかを知る必要がありません。知っていることはすべてディスク上の `.retro/` にあるので、再起動やクラッシュ、同じプロジェクトでの二つ目の OpenCode があっても、何が読まれるかは変わりません。

呼び出しを行わずに省かれるのは、何の証拠も含みえないセッションだけです。指示が一つ、回答が一つ、何も実行されていない場合です。ツール呼び出しがまったくない会話も分析されます。指示ファイルの誤りはまさにそのように現れるからです。誤った回答と訂正があり、何も実行されていません。

これらすべてについて設定するものはありません。モデルも、API キーも、プロバイダーもです。作業は、あなたのセッションがすでに動いているところで動きます。

読むのは、書かれたままのシャドーログです。一行に一つの JSON オブジェクト、一オブジェクトに一ステップ。ツールの結果は記録された時点で `maxOutput` まで頭と尾を残して刈り込まれており、巨大な結果が一つ、いつまでもログに居座ることはありません。分析が答えるのは一つの問いだけです。

> このセッションをもう一度実行するなら、より短く、より真っ直ぐ進むためにプロジェクトの何を変えるべきか。

その答えが `.retro/lessons/` に置かれる教訓の一覧です。

終わったログは一度だけ分析されます。誰も答えなかった指示書は改めて出され、`.retro/selfcheck.md` が「何回尋ねて答えがなかったか」を伝えます。これはログについての判定ではなく、事実として記録されます。読んだが記録できなかった読み手と、そもそも始まらなかった読み手を、プラグインは区別できません。よくある原因は、まだ働いているセッションの受信箱で指示書が待っていることです。プラグイン自身が読めないログは別の話で、それが三度続けば脇に置かれ、その旨が示されます。`/retro` が実行されないプロジェクトは分析されません。

### 抽出が何を手がかりにするか

判断基準はプラグインに組み込まれていません。[`prompts/extract.md`](prompts/extract.md) に置かれ、初回実行時に `.retro/prompts/extract.md` としてプロジェクトに播かれ、そこで編集できます。探す価値のある形を次のように記述します。

- 無駄に終わった作業。同じ呼び出しが繰り返され、その間にどのファイルも変わっていない。
- いったん行われ、その後取り消された編集。後の編集によるものでも、作業ツリーを破棄したことによるものでも同じです。
- 行き止まりまで付き従ったスキル。そのスキルが指示したコマンドが、あとで失敗した場合です。
- 失敗に見えない失敗。「completed」と読めるステータスの裏にある、ゼロでない終了コード。
- 静かに取り下げられたタスク。エージェントが書いた文章の中にしか現れません。
- ユーザーが二度以上与えざるを得なかった訂正。

このファイル自身に、これは出発点でありチェックリストではないと書かれています。

### 提案

ログを読むのはプラグインで、提案を読むのは人です。プラグインは提案で止まり、プロジェクトのファイルは編集しません。

| コマンド | 動作 |
|---|---|
| `/retro` | 溜まったものを分析し、そのうえで教訓を一つ渡します。未決のもののうち最もスコアの高いものです。 |
| `/retro all`（または `/retro-all`） | 同じ分析のあと、待機中の教訓を一つの計画として渡します（`proposeLimit` まで、既定は十）。一度で承認できます。 |

三つめのコマンドはありません。プラグインが機能しているかは `.retro/selfcheck.md` に書かれ、各セッションの最初のプロンプトから、そして終わるときにもう一度書き換えられます。

教訓は、そのコマンドを実行したセッションに、すでにそこにいるエージェント宛で届きます。まずその教訓がまだ成り立つかを判断するよう求め、次にそれを伝えるよう求め、判断が下るまで何も変更しないよう求めます。

```
# retro — lint-skill-no-config

lint スキルは `npx eslint . --fix` を指示しているが、このプロジェクトでは実行できない。

2 セッションで確認、9 ステップを消費、確信度 0.9、スコア 16.2。
最後に見られたのは 3 セッション前。

提案する変更
  AGENTS.md — lint の要求を、コミット済みの ESLint 設定がある場合に限る条件付きにする。

判断が必要
  このプロジェクトは ESLint を設定すべきか、それともこの約束事をやめるべきか。
```

判断は、そのセッションにいる人とエージェントのものです。エージェントはファイル、履歴、そしてプロジェクト自身のスキルを持っており、その教訓が今も当てはまるかを判断する役としてはプラグインより適しています。判断が下ると、エージェントは `retro_decide` ツールでそれを記録します。このツールは帳簿をつけるだけです。却下は記憶され、その教訓は再び提案されません。

`/retro all` は、同じ引き渡しを一度にまとめて行うものです。待機中の教訓が順位づけされてまとめて渡され（`proposeLimit` まで）、エージェントがまだ成り立つものを確かめ、残りをファイル単位でまとめた一つの計画にします。その計画が一度だけ承認されます。

### 修正がどこに属するか

教訓が記録するのは問題です。どこで直すかは引き渡しの際に決まります。エージェントと人が、このワークスペースに実際に何があるかを見てから決めます。ここでハーネスがどの指示ファイルを読むのか、プロジェクト単位または全体のスキルが存在するのか、この作業をすでに扱っているより具体的なものがあるのか、を確かめます。

選べる方法は次のとおりです。

- 指示ファイルを修正する。広く当てはまる事実や制約の場合。
- スキルを修正する。スキルが誤った手順を示した場合、または発動すべきでない場面で発動した場合。
- スキル、あるいは規則が実際に効く範囲に限定した指示ファイルを新しく作る。適切な置き場所がまだ存在しない場合。
- ツールを要望する。足りないものが指示ではなく能力である場合。
- プロジェクトのコードを変更する。罠がコード自体にある場合。明確な合意なしに適用することはありません。
- 置き場所を決めずに残す。正しい帰属が本当に不明な場合。

教訓そのものは常に一つのワークスペースに属します。修正はそうとは限りません。原因がその人のどこでも変わらない働き方にある場合、修正は全体のハーネスに属します。一つのプロジェクトだけで直しても、ほかのプロジェクトでは壊れたままになるからです。プロジェクトの外にあるものは、確認なしに編集されることはありません。

手順とこの一覧は [`prompts/propose.md`](prompts/propose.md) にあり、プロジェクトに播かれ、そこで編集できます。

## 教訓

教訓は YAML フロントマターを持つ Markdown ファイルです。

```yaml
id: lint-skill-no-config
statement: The lint skill assumes eslint; this project has no linter.
evidence:
  - session: a81f
    steps: [41, 58]
  - session: c204
    steps: [12, 19]
cost: 34
recurrence: 3
confidence: 0.9
lastSeen: 41
recordedAt: 2026-10-19T15:16:04.134Z
proposal:
  target: .opencode/skills/lint/SKILL.md
  change: |
    Before running, check for a lint config and a lint script.
    If absent, do not run; report instead.
ask: Is the linter really unused here?
status: new
```

`cost` はその問題が消費したステップ数で、セッションをまたいで合算されます。`recurrence` はそれが現れた独立したセッションの数です。`lastSeen` はその教訓を最後に書き込んだ時点でのワークスペースのセッション通算数です。

### 順位づけ

スコアは `cost × recurrence × confidence × freshness` です。

鮮度は、その問題が現れなかったセッションが `halfLife` 回（既定は十）続くごとに半減します。日数ではなくセッション数で数えます。一日一セッションの使い方では、暦で測る減衰は一晩ですべてを埋めてしまいます。

再発は、一度の高額な事故より重く扱われます。三つのセッションで見られた問題は、四つめでも見られます。

### ライフサイクル

教訓はセッションではなく問題を鍵とします。同じことに遭遇した二度目のセッションは、別のファイルを作るのではなく、証拠を加えて `recurrence` を増やします。

`lessons/` には未決の問いだけが置かれます。承認または却下するとファイルは `archive/` に移り、何も削除されません。`later` としたものは未決のまま残ります。いったん閉じたあとに戻ってきた問題は、同じ問題であることに加えて、その修正が持たなかったという知らせでもあるため、履歴をそのまま保って再び開かれます。固定の上限三十が一覧を短く保ち、あふれた分も同様に保管されます（`later` とされた教訓を除く）。

## インストール

OpenCode が npm からプラグインを取得します。`opencode.json` にパッケージ名を書くだけです:

```jsonc
{
  "plugins": [{ "package": "opencode-retro" }]
}
```

設定するものはありません。プラグインは自分でモデルを呼ばないので、選ぶモデルも、渡す鍵も、つなぐプロバイダーもありません。分析は、それを求めたセッションのサブエージェントとして動きます。`.retro/selfcheck.md` が、それが実行されたか、実行されなかった場合はその理由を報告します。

**まず npm に実際に何があるかを確かめてください。** `0.1.0` より前のバージョンはいずれも名前の placeholder です。エラーも出さずに読み込まれ、コマンドを登録せず、`.retro/` も作らず、何も知らせません。つまり最初の本当のリリースより前にこの設定をそのまま使うと、見た目は普通のセッションと、実際には存在しないプラグインが残ります。`npm view opencode-retro version` が `0.1.0` 未満なら、`package` にはチェックアウトの絶対パスを指定してください。プラグイン自体を開発するときも同じです。相対パスの場合、セッションの起動がエラーも出さずに止まったままになります。固定できるバージョンができたら、正確なバージョンを固定することもできます（`opencode-retro@0.1.0`）。

その他はすべて任意です。

- `dir` — すべてが置かれる場所。既定は `.retro`。
- `prompts` — プロンプトのディレクトリ。既定はその中の `prompts`。
- `halfLife` — 教訓のスコアが半減するまでの「再発しなかったセッション数」。既定は十。
- `proposeLimit` — `/retro all` 一回あたりの教訓数。既定は十。
- `extractLimit` — `/retro` 一回で出す作業指示書の数。既定は無制限。
- `maxOutput` — シャドーログに一ステップごとに保存するツール出力の文字数。既定は 8000。
- `heartbeatMs` — セッション作業中のセルフチェック書き込みの最短間隔。既定は 60000。
- `keepSessions` — 誰も引用していないものも含め、すべてのログを残す。既定では無効。

### ディスク上に現れるもの

プラグインが書き込むものはすべてプロジェクト内の `.retro/` 以下に収まり、提案が受け入れられた場合を除いて他の場所には書き込みません。すべてプレーンテキストです。

```
.retro/
  prompts/
    extract.md       何を教訓とみなすか
    propose.md       教訓をどう引き渡すか、一つでも全部でも
    updates/         新しい既定値。使用されていない
  sessions/          生のログ。未読のあいだ、教訓が参照しているあいだ、この一週間に書き込まれたあいだは保持される
  work/              分析を待つログ一つにつき一通の作業指示書
  lessons/           未決の問い
  archive/           承認済み・却下済み・押し出された教訓
  selfcheck.md       プラグインが機能しているか
  state.json
  plugin.log         フック、コマンド、バックグラウンド処理のエラー
  .gitignore         一度だけ書き込まれ、以後はプロジェクトのもの
  README.md          このディレクトリが何かを、開いた人に伝える。一度だけ書き込まれる
```

ログが削除されるのは、三つの条件がそろったときです。最後まで読まれていること、それを引用する未決の教訓がないこと、そして七日間なにも書き込まれていないことです。教訓の証拠はセッションとその中のステップ範囲を指し示し、レビューの場では「そこで実際に何が起きたのか」という問いに、要約ではない答えが必要になります。だから引用されているログは残ります。七日間という条件があるからこそ、セッションがまだ動いているかを知らなくても安全に削除できます。書き込みを続けるセッションはログを保ち、静かな一週間のあとに再開されたセッションは新しいログを始め、それは最初から読まれます。誰も読んでいないログは、どれだけ古くても削除されません。増え方を決めるのは未決の教訓の数（これには上限があります）と一週間分のセッションであり、プロジェクトの古さではありません。

プロジェクトの `.gitignore` に追記するものはありません。初回実行時にプラグインが `.retro/.gitignore` を書き、git はそれを配下のすべてに適用します。セッション、作業指示書、状態、セルフチェック、プラグインのログ、プロンプト更新のお知らせ、クラッシュが残した書きかけの `.tmp` ファイルは無視され、`lessons/`、`archive/`、実際に使われるプロンプトファイルは無視されません。このファイルは一度だけ書かれ、以後はプロジェクトのものです。

この切り分けは設計であって便宜ではありません。教訓と保管庫はプロジェクトについての知識です。読めて、レビューに現れ、リポジトリとともに移動します。プロンプトはその設定であり、ここで働く他の人と共有する価値があります。残りは差分に雑音を増やすだけです。

### プロンプト

プラグインの振る舞いは二つのプロンプトが決め、どちらもプロジェクト内のファイルです。何を教訓とみなすか、そして教訓をどう引き渡すかです。後者はまとまった場合も扱います。`/retro all` が送るのは同じ規則で、その最後の節が、教訓が一度に複数届いたときに何が変わるかを述べます。一つの計画、ファイル単位でまとめる、見送ったものは名前を挙げる、です。コマンドごとに規則を置かず一つにしてあるので、手を入れても、それと食い違う二つめの写しが残ることはありません。

それぞれ初回実行時に同梱の既定値から種をまかれ、以後書き換えられません。解決の順序はまずプロジェクト、次に `~/.config/opencode/retro/prompts/`、最後に同梱の既定値です。そのためプロンプトは一つのプロジェクトに固定することも、すべてのプロジェクトに固定することも、どちらもしないこともできます。

新しい既定値が公開されると、`prompts/updates/<name>.vN.md` として届き、そのファイルは使用されていないという注記が冒頭に付きます。利用者に代わって適用されるものは何もありません。

ソースに残るのは機械的な部分です。答えの形式、教訓のフィールドの順序、そして判断を記録せよという指示です。形式はプロンプトファイルではなく作業指示書のほうに書き込まれるので、プロンプトを編集して消すことはできません。その機械的な半分は `retro_record` ツールのスキーマで、答えがプラグインに届く前に OpenCode が検証します。

## 動作の確認

フックが登録できたことは何の証明にもなりません。API がもう使っていない名前で登録されたフックは、登録には成功し、その後一度も発火しません。

そのため `.retro/selfcheck.md` は、設置状況ではなく生存状況を報告します。イベントストリームが見たものと、フックが受け取ったものを突き合わせます。このファイルは自身の鮮度の規則も携えています。

> **いま作業しているのに `heartbeat` が数分より古いなら、このプラグインは動作していません。**

これらの確認はファイルが書き込まれるたびに走り、費用はかかりません。プラグインが依存する API の構成、どの層のプロンプトが有効か、そして何が決定を待っているか、です。プラグインと OpenCode のバージョンはファイル冒頭に書かれます。分析が通るかは別に尋ねません。`/retro` のたびに実際に試され、答えの返らなかった指示書はそのまま、あったとおりに報告されます。

## 必要なもの

- OpenCode v2、`@opencode/plugin` 2.0.18 以降。2.0.32 で検証済み。
- OpenCode 以外に必要なものはありません。分析は、あなたが `/retro` を実行したセッションのサブエージェントとして、そのセッションのモデルで動きます。
- 実行時依存はありません。
